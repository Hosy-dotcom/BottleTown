# BottleTown architecture audit

## Scope and evidence

Reviewed the six tracked Luau files, the embedded scripts and settings in `BottleTown.rbxlx`, and the open `BottleTown_Prototype_v0.1.rbxl` place through Roblox Studio MCP in Edit mode. All six scripts matched in byte length and source fingerprint across all three copies after normalizing line endings and trailing whitespace. The open place has a different filename, so script parity alone cannot establish full place parity. The Editor Output query returned no entries. This audit did not start a new playtest, so multiplayer timing, mobile layout, spawned character properties, and runtime Output remain unverified.

## Scripts and dependencies

- [Game.legacy.luau](../ServerScriptService/BottleTown/Game.legacy.luau#L1) is the server entry point. It requires Config, Inventory, Bottles, and Residents, attaches runtime prompts, routes successful pickups and station actions, pulses the machine display, and sends feedback. It expects `workspace.BottleTown`, `ReplicatedStorage.BottleTown.Feedback`, `Pfand station.Display`, and both station `Interaction` parts to exist under their current names.
- [Bottles.luau](../ServerScriptService/BottleTown/Bottles.luau#L27) owns the active registry, initial population, ambient refill loop, and procedural bottle models. It takes a binder from Game and returns a discard callback that Game passes to Residents. Successful pickups call the removal closure to update the registry and destroy the model.
- [Residents.luau](../ServerScriptService/BottleTown/Residents.luau#L23) generates residents, poses them along routes, and requests drops through the callback. It has no inventory or currency dependency.
- [Inventory.luau](../ServerScriptService/BottleTown/Inventory.luau#L6) owns per-player bottle lists, capacity, integer-cent cash, and mythicals. It projects those values into Player attributes. Pickup, redemption, and upgrades all flow through this module.
- [Config.luau](../ReplicatedStorage/BottleTown/Config.luau#L1) provides bottle definitions, the mythical definition, the shared population cap, the upgrade price, and currency formatting. Game and the HUD use the formatter. Bottles uses type definitions and the cap. Inventory uses pricing and formatting.
- [BottleTownHUD.local.luau](../StarterPlayerScripts/BottleTownHUD.local.luau#L44) creates a persistent HUD under PlayerGui, reads attributes, animates the capacity bar, and renders messages from the server-to-client Feedback event. It sends no gameplay requests. The built-in prompt interaction supplies the input path.

## System findings

### 1. Bottle spawning and world population

The server samples 20 distinct entries from 43 authored X/Z positions at startup, cycling regular types. Four-stud separation can reject candidates, so 20 is an attempt count. Every four seconds, ambient refill tries up to five candidate positions for at most one successful addition while the total is below 22. Residents can add bottles up to the shared hard cap of 24. The two-slot difference leaves immediate drop opportunities while residents can also occupy the rest of the population. There are no source quotas, expiry, or recovery if a model is removed outside its pickup closure. Such removal would leave a counted entry and block nearby spawns. The bookkeeping currently assumes the binder and destroy path always complete successfully. [Spawn and cleanup](../ServerScriptService/BottleTown/Bottles.luau#L35)

All 43 fixed positions hit a surface between Y 0.04 and 0.18 in a downward raycast against the open Studio map. This supports the flat-map assumption for those points today. Runtime placement uses a fixed height formula, so raised ground, obstacles, and resident drops need separate validation as the town changes. Ambient refill can also stall when sampled sites are occupied or too close to active bottles. The mythical has a 1-in-1,800 roll on eligible unforced spawns, including resident drops, and can spawn once per server lifetime. It bypasses bag capacity and has no persistence, so its collection value and expected availability need an explicit design decision. [Population policy](../ServerScriptService/BottleTown/Bottles.luau#L40)

### 2. Bottle pickup and ProximityPrompt interactions

Game creates default prompts with E and built-in touch input. Pickup is immediate. The handler checks for a living humanoid, character root, enabled prompt, target under the town, and distance within the configured radius plus one stud. A server-side claim flag prevents two successful awards on one bottle in the current non-yielding path and is released when collection fails. The bottle value is bound server-side. [Interaction and claim](../ServerScriptService/BottleTown/Game.legacy.luau#L9)

Prompt and server checks both allow interactions through geometry within range. That may be acceptable for the current open spaces, but walls or adjacent interiors make it a map-dependent fairness risk. Distance checks establish proximity to the server-observed character position and do not establish legitimate movement. There is no action rate limit, so repeated valid-range attempts, including empty returns or full bags, can repeatedly invoke server work and feedback. Preserve the claim and keep animation, persistence, or other yielding work outside the commit. A future hold must validate elapsed time on the server, since the built-in hold settings and client-originated events are UI signals. [Roblox client-server security](https://create.roblox.com/docs/scripting/security/client-server-boundary)

### 3. Player inventory and cash

Profiles start with five slots and zero cash. The list stores server-provided bottle definitions, and redemption calculates value from those definitions. The server replicates four display attributes. There is no DataStore or other persistence, so bottles, cash, upgrades, and stars reset after leaving or changing servers. Player profiles survive character respawn in the same server. The separate attribute writes can make client UI refresh repeatedly and briefly combine old and new values during a transaction. This matters more if later UI requires a coherent transaction view. The shared attributes also make these totals available on replicated Player instances. Treat them as public presentation data. [Profile lifecycle and publishing](../ServerScriptService/BottleTown/Inventory.luau#L6)

### 4. Pfand return machine

Studio confirmed an anchored, invisible, non-colliding `Interaction` part and a separate `Display` part at the Pfand station. The eight-stud prompt returns all eligible bottles at once. The server clears the bag and credits the sum in one non-yielding call. An empty bag returns an error message. Successful returns cancel any prior color tween and restart a shared 0.9-second pulse. The code has no per-user machine session, insertion slot animation, or per-bottle transaction. Concurrent users can each return their own inventory, and the shared pulse reflects the latest success. [Station binding](../ServerScriptService/BottleTown/Game.legacy.luau#L44) · [Redemption](../ServerScriptService/BottleTown/Inventory.luau#L40)

### 5. Equipment upgrades

The shop uses the same prompt helper at its own anchored interaction point. A single €2.00 purchase changes capacity from five to ten, with balance checks and duplicate-purchase protection under the current two-capacity model. Price is shared config, while the target capacity and copy appear in both Game and Inventory. Capacity doubles as the purchase marker. Additional tiers or capacity bonuses would make that equality check fragile. Introduce an explicit equipment tier with derived stats and text when adding a second upgrade. [Shop binding](../ServerScriptService/BottleTown/Game.legacy.luau#L63) · [Purchase](../ServerScriptService/BottleTown/Inventory.luau#L53)

### 6. NPC generation, movement, and scaling

Mara, Emil, and Ada are generated as seven anchored, non-colliding parts each. Server tasks interpolate fixed routes at nominally four studs per second and pose the limbs about every 40 ms. One marked stop per route has a 65% chance to request a drop. The request can be rejected by the shared cap or separation rule. The models use hard-coded dimensions, a fixed ground origin at Y 0.14, and procedural limb swings. There is no Humanoid, rig, pathfinding, collision response, or dynamic floor following. Routes must be rechecked when the map changes. Scaling dimensions alone would leave joint offsets and foot placement out of proportion. More residents would multiply replicated part updates, so profile those costs before increasing density. The RunService import is unused. [Resident generation and routes](../ServerScriptService/BottleTown/Residents.luau#L1)

### 7. Player character configuration

Studio reported character autoload and appearance loading enabled, walk speed 16, jump-height mode at about 7.2 studs, and camera zoom from 0.5 to 128 studs. StarterCharacterScripts was empty, and there was no custom StarterCharacter or custom character setup in the source. The saved AvatarSettings instance had no visible serialized override payload. Runtime rig type, scales, and dimensions were not verified. Current avatar loading and the procedural residents have no shared height or attachment standard. A character policy change therefore affects animation compatibility, backpack fit, prompt reach, camera, and map clearance together. [Roblox Avatar Settings](https://create.roblox.com/docs/studio/avatar-settings)

### 8. Client-server architecture

The economy, bottle lifecycle, entitlement checks, and NPC drop requests are server-owned. The only place-defined remote found in the gameplay containers was Feedback, used server-to-client. Replicated Config exposes prices and appearance definitions without giving clients write authority over the server module. Keep the HUD and effects as consumers of server results. Preserve server ownership of item identity, eligibility, price, and commit order when adding input remotes. Streaming is enabled in the open place, so local decorations and UI attached to world objects must handle instances streaming out and returning. [HUD subscription](../StarterPlayerScripts/BottleTownHUD.local.luau#L70) · [Feedback sender](../ServerScriptService/BottleTown/Game.legacy.luau#L28)

### 9. Script Sync and organization

Studio contains one enabled server Script, one enabled LocalScript, and four ModuleScripts. The local `StarterPlayerScripts` directory corresponds to `StarterPlayer.StarterPlayerScripts`; Config is under ReplicatedStorage and the four server files are under ServerScriptService. The file suffixes follow Studio Script Sync conventions. The tracked Luau files are the script-editing source of truth. The place snapshot also embeds the same six scripts and owns the world, remote, and instance settings. Starting with the wrong place file or changing an anchor name can break the direct lookups in Game. A broken station dependency can stop initialization before Residents starts, after the bottle loop has already begun. Verify required instance types and paths at startup during a future refactor. Current file-to-instance source parity was verified. The active Script Sync directory links and live write-through were not verified. No second runnable copy was found in the inspected Studio containers. [Roblox Script Sync](https://create.roblox.com/docs/scripting/sync)

### 10. Animations, audio, and visual assets

The inspected edit containers had no Sound, Animation, Accessory, MeshPart, or SpecialMesh instances. No custom pickup animation, pickup or return audio, or backpack asset appeared in source. Runtime Roblox avatar assets were outside the inspection. Resident walking is procedural, the machine display and HUD bar use TweenService, and bottle visuals are generated from primitive parts, highlights, and a mythical light. The town uses primitive parts, SurfaceGui signage, point lights, and a particle emitter, with sky and post-processing in Lighting. Preserve the prompt body and station interaction anchors when remodeling. [Bottle parts](../ServerScriptService/BottleTown/Bottles.luau#L43) · [Resident posing](../ServerScriptService/BottleTown/Residents.luau#L41)

## Change boundaries and priorities

- **Safe to change in isolation.** HUD copy and styling can change while preserving attributes and Feedback. Bottle materials and decorative pieces can change while preserving the prompt anchor, scale assumptions, and removal ownership. Resident pose styling can change while preserving route timing and the drop callback. Station decoration can change while keeping the named interaction and display parts compatible.
- **Shared contracts.** Pickup duration crosses Game, equipment stats, user input, and bottle claims. Per-bottle returns cross station input, inventory, cash, and presentation. Population rules affect resident visibility, spawn availability, and mythical odds. Avatar policy affects the player controller, animation assets, backpack attachment, routes, and environmental clearance. Make these changes in small increments with verification at each boundary.
- **Cleanup candidates.** Remove the unused RunService import during resident work. Centralize capacity and upgrade text when equipment tiers are introduced. The embedded script copies are a synchronization risk and part of the place snapshot. There is no evidence of duplicate runtime gameplay handlers or abandoned alternate implementations.

## Recommended feature design

1. **Upgradeable pickup duration.** Derive duration from the server-owned equipment tier and snapshot it when a pickup starts. Use per-player progress UI for keyboard and touch, since one replicated prompt duration applies to the shared bottle. Keep one pending attempt per player with a server start time and target identity. Recheck the active target, distance, character state, and current capacity before commit. Cancel attempts on range loss, respawn, or disappearance. Add server rate limits and define the winner as the first valid completion. Keep the final check, award, and removal together without yielding. [Roblox prompt security](https://create.roblox.com/docs/scripting/security/client-server-boundary)
2. **Pickup animation and sound.** Play cancellable local anticipation during the hold and play completion cues from a structured server success result. Keep success effects independent of the bottle instance after it is removed. Use the character rig selected for the avatar policy, and handle interrupted tracks and respawns. If nearby players should see or hear the outcome, replicate a bounded world cue tied to the confirmed action.
3. **Interactive bottle returns.** Add a server operation that consumes one eligible bottle and credits that bottle's configured value in the same commit. A simple first version can return the next eligible item in order. Add per-player station state, request pacing, distance checks on every insertion, and duplicate-request handling if a custom remote is used. Report the credited amount and remaining count after each commit, then play the insertion effect. Decide separately whether the display is a shared effect or represents a machine reserved for one player.
4. **Visible backpacks.** Attach a visual model at spawn using a validated rig attachment. Drive a small set of fullness variants from the server-owned count and derived capacity. Handle count changes, tier changes, respawns, and late observers. Keep decorative parts light, non-colliding, and out of the pickup and movement logic.
5. **Controlled bottle population.** Keep one authoritative population manager for both sources. Replace fixed height placement with validated surface markers or ground checks, and add per-zone targets, an explicit resident budget, and bounded refill work. Use one idempotent removal path for pickups and invalidated models. Give rare collectibles their own lifetime and spawn policy so population tuning has a predictable effect on rarity.
6. **Consistent player and NPC scaling.** Pick a documented target rig and standing height for players, and verify it against representative avatars in Studio. R15 with Roblox's consistent gameplay preset is a candidate for standardized collision and animation. Use the same standing-height target for residents, either through matching rigs or by scaling both dimensions and pose offsets from a ground-relative origin. Verify reach, bag fit, collision, and walking over representative parts of the map. [Roblox Avatar Settings](https://create.roblox.com/docs/studio/avatar-settings)

## Playtest checks for the first implementation

Use two clients to confirm exactly one player receives a contested bottle, an interrupted or out-of-range hold earns nothing, and a full bag doesn't consume the bottle. Check touch and keyboard input, respawn and streaming, exact one-bottle cash credit on repeated insertion requests, and simultaneous station use. Exercise cap saturation, failed spawn attempts, external model removal, and mythical availability. Compare bag fit, reach, and NPC footing against representative avatars, and review both server and client Output during the run.
